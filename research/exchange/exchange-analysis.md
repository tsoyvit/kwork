# Анализ Биржи Kwork для IT

Дата живого среза: 2026-08-10. Сырые примеры: [`data/exchange-sample.csv`](../../data/exchange-sample.csv).

Этот блок дополняет карточную выдачу: кворки показывают, **как исполнители продают**, а Биржа — **что заказчики прямо сейчас формулируют как задачи**.

## Что видно по живым проектам

В одном коротком срезе одновременно встречались:

- 1 000 ₽ — WordPress → Telegram notification;
- 500/1 500 ₽ — развёртывание сайта 1С-Битрикс на готовом шаблоне;
- 3 000/9 000 ₽ — WordPress parsing/automation;
- 3 000/9 000 ₽ — WordPress + local TTS;
- 5 000/15 000 ₽ — Telegram bot;
- 5 000/15 000 ₽ — AI sales agent;
- 10 000 ₽ — доработка существующего сайта;
- 20 000 ₽ — Android application fixes;
- 20 000/60 000 ₽ — deployment готового automation/content system.

То есть реальный IT-поток не распадается на «дешёвые задачи» и «серьёзную разработку» — они идут параллельно. Это аргумент в пользу широкого intake.

## Предложения на проект сильно различаются

В наблюдённой выборке были проекты с:
- **0** предложений;
- 3–4;
- 15–27;
- 44–53;
- 72 предложениями.

Это означает, что количество откликов полезно как **приоритет по времени**, но не как фильтр `не участвовать`. Высокий proposal count не отменяет заказ, если у нас есть сильный matching case и понятное решение.

## Процент найма заказчика — полезный коммерческий сигнал

В живой выборке были hire rates от 20% до 80%. У некоторых активных покупателей сотни предыдущих покупок и десятки/сотни проектов.

Практическое использование:

- высокий hire rate + большая история покупок → особенно хороший кандидат на быстрый ответ;
- низкий hire rate → не запрещает отклик, но снижает приоритет, если одновременно есть более «горячие» заявки;
- заказчик с 0–1 проектом — не автоматически плохой, просто меньше данных.

## Очень дешёвый budget не обязательно означает маленькую задачу

Пример: проект 1С-Битрикс с желаемыми 500 ₽ просил развернуть шаблон, настроить функционал, заполнить контентом и сдать на хостинге. Поэтому **budget заказчика нельзя использовать как proxy сложности**.

Нам нужно быстро оценивать scope независимо от цифры, затем решать, можно ли выгодно предложить урезанный MVP/base scope или свою цену.

## Большие задачи часто приходят как «не с нуля»

Хороший пример — content factory: код и документация уже существуют, нужен deploy, API connection, WordPress REST, cron/systemd, backup и месячная поддержка. Это отдельный класс заказов, который особенно хорошо подходит стратегии `берём широкий технический спектр + используем Codex для входа в чужой проект`.

## Реальные cross-stack задачи

Заказчики часто формулируют задачу сразу на стыке технологий:

- WordPress + parser + SEO + scheduler;
- WordPress + Python + TTS + queue;
- Telegram + payments + DB + admin + deploy;
- Linux + Python + API + WordPress REST + Google Sheets;
- AI + Telegram/WhatsApp + CRM/Sheets;
- Android + Google Play API requirements + bug fixing.

Следствие: профиль, искусственно ограниченный одной технологией, действительно терял бы большой слой потенциальных заказов.

# Модель приоритизации Биржи

Мы не делаем hard-filter по цене/конкуренции/стеку. Приоритет нужен только для очереди ответов.

## P0 — отвечать сразу

- задача понятна;
- можно быстро оценить решение;
- сильное совпадение с нашим опытом/готовым case;
- заказчик реально нанимает;
- работа небольшая или быстро стартует;
- мало предложений — дополнительный плюс, но не обязательное условие.

## P1 — отвечать следом

- работа хорошая, но нужно 10–20 минут на изучение документации/репозитория/API;
- средний/высокий бюджет;
- есть шанс на продолжение.

## P2 — отвечать после P0/P1

- scope мутный;
- budget выглядит плохо относительно объёма;
- заказчик редко нанимает;
- много неизвестных.

Но P2 не означает `пропустить навсегда`, если есть свободный ресурс.

# Что должна делать будущая система мониторинга

Для каждого проекта показывать одним сообщением:

- title + URL;
- бюджет / допустимый бюджет;
- buyer purchases / number of exchange projects / hire rate;
- proposals;
- краткую decomposition задачи;
- предполагаемый scope;
- релевантные portfolio cases;
- риски/вопросы;
- draft ответа;
- priority P0/P1/P2.

Главная роль AI здесь — **сократить время от появления проекта до качественного персонального ответа**, а не автоматически отбрасывать большую часть рынка.
